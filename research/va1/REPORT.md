# VA-1 report: can the two sides disagree about what is valid?

2026-11-23. The numbers are generated by `analysis/analyze.ts` into `results/analysis.md`
(`npx tsx analysis/analyze.ts` reproduces them). The pre-registration and its amendments are in
PREREGISTRATION.md; the spec is docs/experiment-va1.md.

## Result in one paragraph

**The prediction did not hold.** The experiment predicted that on cross-field and computed rules, a
schema-driven client would drift from its server and Canon would not. With reference solutions
written carefully, validation agreement was **1.000 in all three arms on both sets**: 120 of 120
references, 40,000 inputs per arm, zero bounces and zero blocks. The primary comparison (Canon minus
Schema-driven, Set 2) is **+0.000 [0.000, 0.000]: non-inferior, not a win.** The experiment tested
the tools' ceiling, and found that a careful author writing both sides, with the rule list in front
of them, does not drift on this rule subset in any arm. The agent phase is inconclusive: Qwen 7B
completed 2 of 40 recorded runs, so there is nothing to compare. Spend was USD 0.

## What this means for the claim

- **Not supported:** "when rules are written twice, client and server must drift, and Canon is the only
  way out." A careful author does not drift here, and the schema-driven arm closes the gap even on
  cross-field rules (it uses hand-written checks for what a schema cannot state, written alongside
  the server's).
- **Still standing from FS-1:** the large gap (100% against 43% to 59%) came from clients that had
  *no* validation, or looser validation, in the agent-written arms and in some reference clients.
  That is a gap in effort and discipline, not in what the tools can express. Canon removes the
  effort: the rule is written once, and the client check is generated. VA-1 did not measure effort,
  so this paragraph is an interpretation, not a result.
- **The honest headline** is therefore weaker than the one the plan hoped for: *Canon makes
  agreement automatic; careful hand-written code can match it.* What Canon removes is the work and
  the chance of forgetting, not an expressiveness limit.

## Phase 1: references only (the tools' ceiling)

All 40 tasks verify in all three arms (120 of 120 references pass their hidden tests and the arm's
checks); none dropped. Agreement is 1.000 in every input category (base, inside, outside, random)
in every arm. With and without the four adapted tasks (`gift-card`, `signup-password`, `invoice`,
`range-filter`) the result is the same (n=20 and n=17 on Set 2). The schema arm's chain is
Pydantic, OpenAPI, openapi-typescript 7.13.0 for types and ajv 8.17.1 for validators; a probe model
covering every constraint kind showed no disagreement on 49 inputs
(`results/schema-enforcement.json`). The input generator is tested (`harness/generator.test.ts`)
and checked against every reference server: base and inside inputs get 2xx, outside inputs get 422.

### Why not to read this as "the tools are equivalent"

1. **The references are the best case for the hand-written and schema arms.** Each author wrote both
   sides with the rule list in view.
2. **The references are less independent than the spec asked.** For 28 of the 40 tasks (batches B
   to D), all three references were emitted by throwaway scripts from one author's template. Each
   arm's code is different code, but the design choices share one origin, which can suppress the
   kind of drift real teams produce.
3. **Exotic Unicode was not probed.** The generator uses ASCII whitespace plus a few emoji at length
   edges. JavaScript `trim()` against Python `strip()`, and `\s` against a Rust-regex `\s`, are
   known to differ on characters such as NEL and U+001C, and drift there is plausible. The M4
   validator test did probe these and found Canon consistent, but the hand and schema arms were not
   probed on them here. **This is the most promising place for a follow-up.**
4. **Scope limits, not results.** No task uses a pattern, a per-element list rule or a rule over a
   value inside an Option, because Canon's portable `requires` cannot state them. So Set 1 could
   only ever show a tie, and the comparison excludes exactly the cases where a schema is more
   expressive than Canon.
5. **Some single-field bounds are implied by a cross rule,** so a few outside inputs break two rules.

## Phase 2: agents write the arms (Qwen 7B, exploratory, inconclusive)

Only 40 of 360 planned runs exist (run 1 for the alphabetically first tasks; each run takes about
5 minutes). The runs that failed because the shared MLX server died were rerun, as pre-registered.

| arm | runs | completed | checks ok |
| --- | --- | --- | --- |
| hand | 14 | 2 | 1 |
| schema | 13 | 0 | 0 |
| canon | 13 | 0 | 0 |

Canon runs often lacked the endpoint (404) or failed `canon check`; schema runs often failed on a
Pydantic `EmailStr` needing the uninstalled `email-validator`, or on the checks. Agreement is only
defined on completed runs, so the primary comparison has no data. The two completed hand-arm runs
had agreement 0.753 (Set 1) and 0.981 (Set 2): an anecdote, but it points where Phase 1 could not
look, that a model's own hand-written client can drift from its own server. The Canon arm's
reference costs about 3,811 tokens, and the 7B model did not turn them into working code, which
matches CanonBench's finding on this model.

## What was not run

GPT-6.2 Sol, Claude Opus 5.5 and Qwen 32B. The OpenAI and Anthropic accounts are out of credit and
the 32B weights failed to download. To run GPT-6.2 Sol: refill the OpenAI account (about USD 20 under

by design. Phase 2 runs 2 and 3 and the remaining run-1 tasks were not run.

## Deviations from the spec

The harness is an adapted copy of FS-1's, with research/fs1 untouched. Agreement on agent runs
counts completed runs only (pre-registered), with a "not completed = 0" variant shown. A compiler
bug found here, an `api fn` with the same name as its `.cn` file shadowing the generated module so
that every valid request returned 500, is fixed on main (544cb6c) with a regression test.

## What this suggests next

1. **Unicode-edge inputs for the hand and schema arms.** Run the same 40 tasks with a generator that
   includes NEL, U+001C to U+001F, zero-width characters and astral characters at the length edges,
   and with `trim`-sensitive rules. This is where JavaScript and Python are known to disagree.
2. **Independent references.** Have separate people or agents write the hand and schema arms from
   the task text alone, without a shared template, and without seeing the rule list in code form.
   That measures drift as it occurs, not as it is avoided.
3. **Agents that complete.** A model strong enough to finish the tasks (a refilled GPT-6.2 Sol, or
   Opus) is needed for Phase 2; Qwen 7B cannot produce completed runs in the Canon or schema arms.
