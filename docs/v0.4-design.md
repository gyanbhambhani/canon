# Canon v0.4: design

2026-11-22. Status: implemented on this branch. Every number below was measured offline with local
Qwen2.5-Coder base models (1.5B fp32 and 7B fp16); no model API was called.

v0.4 ships three things:
1. **Effects on function types**, which close the higher-order effect leak, so every function's
   own signature bounds what it can do (`fnEffects` switch).
2. **Canon-Py**: Canon's semantics and guarantees in a strict subset of typed Python syntax, as an
   **opt-in** surface (`py` switch, `--syntax py`).
3. **`canon build` and `--watch`**.

**The default syntax stays brace syntax. Experiment 1 decides whether Canon-Py becomes the default**
(docs/roadmap-to-1.0.md): only if agents are at least as correct with it as with v0.3 syntax, at
lower cost. The measurements below are the evidence for offering the switch, and they also show
why the switch should not be flipped on the proxy alone.

## Goal and constraints

The owner's goal: agents should find Canon as natural as the language they know best (Python), so
they think less and spend fewer tokens, while Canon keeps the guarantees Python lacks:
- types on every signature, always checked;
- effects declared in the signature, with undeclared or unused effects an error;
- `Result` instead of exceptions;
- exhaustive matching with generated fixes;
- one canonical text per program;
- compiler patches and `--fix`;
- contract fuzzing;
- sealed effects and the capability guard.

**Same AST.** The Canon-Py front end (packages/compiler/src/pylexer.ts, pyparser.ts,
pyprinter.ts, pynormalize.ts) parses to the AST v0.3 uses, so the type checker, effect checker,
code generator and runtime are shared. Only the wording of syntax-specific messages and the
spelling of types in messages follow the surface.
- Every Canon-Py spelling therefore maps onto an existing node.
- Python forms with no Canon meaning are rejected with a message that names the Canon form, not
  added: methods, list indexing, `continue`, exceptions, comprehensions, keyword arguments to
  functions, default arguments, docstrings, `//`, `**`, case guards and multi-statement case bodies.
- This is the decisive difference from the v0.3 prototype (research/v0.3/canonpy), which also took
  Python's library: indexing, methods, comprehensions, `sorted`, `str()`.

## Evidence for the rulings

research/v0.4/likelihood (constructs_v04.py, REPORT.md). Each construct is spelled several
equivalent ways inside three small programs written in the candidate v0.4 surface. Each program is
scored by total log-probability after the header `# A Canon source file (main.cn). Canon is a
strictly formatted, effect-typed subset of Python.`

**Δ** is the chosen spelling minus the best alternative, in nats, averaged over the three contexts;
positive means the model agrees with the ruling. The count in parentheses is the number of contexts
in which the chosen spelling beats every alternative.

## Rulings against the model, or not decided by it

- **Contracts stay decorators.** The cost is 12.8 nats where contracts are used under 1.5B and 1.3
  under 7B. The model prefers `assert` at entry and an `assert` on a `result` variable before one
  `return`. A contract is part of the signature: it is checked on every return, fuzzed by
  `canon test`, skipped by `--no-contracts`, and blamed with R001/R002. An `ensures` written as
  an assert covers only the return it precedes, and reading a body's leading asserts as `requires`
  would silently turn existing asserts into fuzzed contracts. Contracts appear in about a quarter of
  Claude's benchmark programs.
- **Sum types use the compact line.** It ties with one dataclass per variant. With dataclasses,
  `Circle` would look like a type usable in a signature, which Canon rejects, and the one line says
  where the closed set of variants is, which is what makes exhaustiveness checks possible.
- **Pipelines are dropped.** It is a tie, Python has none, and one fewer rule shortens the reference.
- **Splits between the models** (effects decorator vs comment, `class` vs `@dataclass`, `?` vs
  `try_`): each margin is under 2 nats and none holds in all three contexts. We kept the 1.5B
  winner, the shorter or checked form.
- **`//` and `**` are rejected and `/` is kept.** Same AST and runtime means Canon's arithmetic:
  Int `/` truncates toward zero, and `%` takes the dividend's sign. A Python reader expects float
  `/` and flooring `//` and `%`. The type checker catches the common case (a float where an int is
  produced), but not negative operands. This is the largest remaining semantic trap, and the
  Canon-Py reference calls it out in bold.

## Semantics of the Python-shaped forms

- **Bindings.** `x = e` binds a new name when `x` is not visible, and otherwise assigns (and the
  original binding becomes mutable).
  - Scopes are Canon's (block scoped). A name first bound inside an `if` is not visible after it,
    and T002 adds a hint to bind it before the block.
  - When fmt prints any program as Canon-Py:
    - `let x = x` is dropped;
    - an unassigned `var` becomes immutable, and an assigned `let` mutable;
    - a `let` that shadows a visible name is renamed `x_2`, because shadowing has no Canon-Py spelling.
- **Parameters.** Assigning a parameter makes the parser insert a hidden `var p = p`, which the
  printer omits.
- **match.** Python's statement form maps onto Canon's match expression:
  - every case body is exactly one statement, and all cases end the same way;
  - a case body may itself be such a match;
  - a match on a Bool with `True`/`False` (or `_`) arms prints as `a if c else b`;
  - a non-Bool match nested inside a larger expression (legal in braces since v0.2) cannot be
    written in Canon-Py: converting it reports S001, without a patch, because moving the match out
    could reorder effects.
- **f-strings.** `f"a{x}b"` is `"a" + to_string(x) + "b"`. A `+` chain of literals and `to_string`
  calls (at least one of each) prints as an f-string.
- **Tests.** `def test_adds_two() -> None:` is the test "adds two".
- **Python keywords used as Canon names.** Statement words Canon lacks (`from`, `with`, ...) are
  rejected only where a statement starts, so a parameter may be called `from`. Hard keywords that
  Canon allows as names (`case`, `pass`, `is`, ...) are renamed `name_` when converting.
- **Lenient input.** Single quotes, `@dataclass`, `x = x + 1`, `contains(xs, x)`, `== None`,
  `|>`, `|x| e`, `&&` and `t.0` are all read, and C001's patch rewrites them to the one form.

## Effects on function types

`fn(String) -> Unit effects: io` (brace) / `Callable[[str], None, io]` (Canon-Py).
- Calling a function value performs its type's effects, which the caller declares (E101 with a patch).
- An effectful function used where the expected function type allows fewer effects is T011, with no
  patch: either fix changes a contract. Uses covered: argument, record field, list element, return
  value, or a lambda that calls one.
- The standard library's higher-order functions take pure functions, so `map(xs, print)` is T011;
  effect polymorphism is left for later.
- Red-team programs (tests/effects/fx_*.cn) cover parameters, record fields, lambdas, generics,
  nested passing, lists and returns. Each must be rejected, and each is accepted again under
  `--no-fn-effects`.

## Measurements of the implemented surface

research/v0.4/surprisal (corpus.py, score.py, analyze.py, RESULTS.md). The corpus covers all 50
benchmark tasks:
- **Canon**: the modal final programs of the v0.2 benchmark (all pass the hidden tests), formatted
  in brace syntax and **converted to the implemented Canon-Py by `canon fmt --syntax py`**, so the
  two Canon rows are the same programs in two surfaces;
- **TypeScript**: the modal TypeScript programs;
- **typed Python**: hand-written and idiomatic.

Prefixes are a one-line header (bare) or each surface's own agent reference (for-agents.mdx or
for-agents-py.mdx). The values are means per program, with 95% bootstrap intervals over tasks.
Nodes are syntax-tree nodes; Canon's count is its AST, which both surfaces share.

What this says:
1. **The surface helps when the model has no documentation:** about 12 to 13 nats less per program
   (11 to 13%), and 8.6 fewer tokens (10%). It also lowers surprisal per character and per node, so
   familiarity, not only length, drops.
2. **With each surface's own reference, Canon-Py is slightly *more* surprising than brace syntax**
   (about +3 nats under both models, intervals excluding zero for Claude's programs). Under 7B, the brace
   reference lowers brace programs by 43 nats and the Canon-Py reference lowers Canon-Py programs by 27 (1.5B: 41 and 25).
   One reading is that a model already expects Python-shaped text, so a reference has less to add,
   and the reference-conditioned score per token is higher in Canon-Py.
3. **Where Python still wins: everywhere.** Canon-Py with its reference stays 20 to 27 nats per
   program above idiomatic typed Python, and 20 tokens longer. The v0.3 prototype matched Python
   because it used Python's library and idioms. The implemented Canon-Py, which keeps Canon's
   library (no methods, no indexing, `map`/`filter` with lambdas, hand-written helpers), is 45 to 52
   nats above that prototype on the same tasks. **Most of the prototype's advantage was library,
   not syntax.**
4. **Against TypeScript,** Canon-Py with its reference is about even (the intervals include zero)
   and 31 tokens shorter.

**Tokens.** Qwen tokens per program (the only tokenizer available offline; the v0.3 token study used
it too): Canon brace 87.9, Canon-Py 79.3, TypeScript 110.6, typed Python 59.7. Canon-Py saves about
10% of code tokens over brace syntax on the same programs. As in v0.3, code is a small share of an
agent's output, so this alone moves cost by about 2%.

**Limitations.**
- Base-model surprisal is a proxy, not agent behaviour.
- The Canon-Py programs are Canon programs converted mechanically, so they keep Canon idioms;
  fresh idiomatic Canon-Py might score better.
- The Canon-Py reference is new, while the brace reference has been revised through two benchmark
  rounds.
- Experiment 1 is the test that decides.

**Migration check** (research/v0.4/roundtrip.ts, over the benchmark's 2,000 model-written Canon
programs): 1,998 convert to Canon-Py, check clean, and compile back to identical JavaScript. The two
exceptions are GPT-6.2 Sol `rpn` programs with a match nested in an expression (S001). In-repo
corpora: tests/py holds every example and tests/run program in Canon-Py, with identical output.

## Compatibility and modes

- The parser reads both surfaces in every mode, detecting Canon-Py per file. A file is Canon-Py
  when a top-level line starts with `def`, `class`, `@`, `import` or `from`, or when it fails to
  parse as braces but parses as Canon-Py. `canon fmt --syntax py --write` converts to Canon-Py,
  and `canon fmt --write` converts back.
- `--v0.3` (compiler `features: V03`) and `--v0.2` keep those languages. The conformance test still
  holds the oracle byte-exact in both modes for every construct they did not change; v0.4 changes
  no brace layout rule.
- The Canon-Py agent reference (/llms-py.txt) mirrors the brace one section by section (a test
  keeps the headings identical) and is under the 4,000-token budget. research/v0.4/canon-py-arm.ts
  is the Experiment 1b arm: it asks for output word for word as the `canon` arm does, and all 60
  hard tasks' reference solutions, converted, pass it.
