## Summary

v0.5 makes Canon the language agents think in for full-stack features: the agent writes types, API endpoints and business logic once in Canon, and Canon compiles them to a FastAPI backend and a typed TypeScript client that look hand-written.

The frontend and backend can no longer disagree, because both are generated from one source. A field renamed in Canon is renamed on both sides. A validation rule written once is enforced on the server and checked in the client before a request is sent. An endpoint's effects (which tables it touches, which hosts it calls) become a permission list a human can read before it runs.

The UI stays in React and TypeScript, which agents already write well, and calls the generated client. Canon owns the parts where the two sides must agree.

Done means:

- [ ] An example app (examples/todos/) builds with one command into backend/ (FastAPI) and frontend/src/canon/ (TypeScript), and its end-to-end tests pass.
- [ ] Generated Python passes ruff check, ruff format --check and mypy --strict. Generated TypeScript passes tsc --strict, prettier --check and eslint.
- [ ] Every Canon expression used in a contract or business logic gives the same result in the JavaScript runtime, the generated Python and the generated TypeScript (the semantic parity suite).
- [ ] Editing a generated file by hand is caught by canon check and refused by canon build.
- [ ] canon manifest lists every endpoint with its route, effects and validation rules.
- [ ] The Experiment FS-1 harness runs a 10-task pilot in all three arms, and its pre-registration is committed before the main run.

## Scope

v0.5 covers the contract between frontend and backend, the logic behind each endpoint, and simple storage; everything else is out until the experiment shows the approach works.

| In v0.5 | Out of v0.5 |
| --- | --- |
| Project-local modules with explicit named imports | User interfaces in Canon (React stays in TypeScript) |
| `api fn` endpoints with routes, typed inputs and outputs, and typed errors | Authentication, sessions and cookies |
| Validation written once as `requires`, enforced on the server and pre-checked in the client | Database migrations (a schema change resets the development database) |
| Tables of records with get, insert, save, delete and scan | Indexed or SQL-level queries (scans filter in memory) |
| Per-table `store(...)` and per-host `net(...)` effects | Async code, websockets, streaming, file uploads |
| Python backend: Pydantic v2 models, FastAPI routes, plain logic functions, SQLite storage | Other backends (Node, Go) |
| TypeScript output: types, validators and a typed fetch client, with no runtime dependencies | Other frontends or a framework-specific client |
| canon.toml, canon build, canon dev, canon manifest, drift protection | Deployment, hosting and package publishing for generated apps |
| Both surfaces: brace syntax (default) and Canon-Py, through the shared syntax tree | Changing the default syntax (Experiment 1 decides that) |

The existing single-file workflow (canon run, canon test, canon build to JavaScript) keeps working unchanged.

## Language additions

v0.5 adds five things to the language: modules, `api fn`, tables, effects with arguments, and a few built-ins. All of them parse to the shared syntax tree, so brace syntax and Canon-Py both get them. Examples below use brace syntax; the Canon-Py spelling of each is given in one line.

### Projects and modules

- A project is a folder with a canon.toml. Source files live under its src folder (default canon/).
- A module's name is its path without the extension, with folders joined by dots: canon/billing/invoices.cn is billing.invoices.
- Imports name what they take: `use todos.{NewTodo, Todo}`. No wildcards, no renaming, no cycles. A cycle is M002 and an unknown name is M003. Every top-level item is visible to importers; there are no visibility modifiers in v0.5.
- Canonical form sorts import lines by module and the names inside each.
- `use std.<name>` works as before. A single file with no canon.toml is still a valid program.
- Canon-Py: `from todos import NewTodo, Todo`.

### API functions

```
api fn create_todo(input: NewTodo) -> Result[Todo, TodoError]
  route: POST "/todos"
  effects: store(todos)
  requires: str_len(trim(input.title)) > 0
{
  ...
}
```

- An `api fn` is an ordinary function plus a `route:` clause. Clause order is route, effects, requires, ensures. It can be called from other Canon code and tested with canon test like any function.
- Route: method GET, POST, PUT, PATCH or DELETE, then a string literal path starting with /. A `{name}` segment binds the parameter of the same name, which must be Int or String.
- Inputs: for GET and DELETE, every parameter not in the path is a query parameter (Int, Float, Bool, String, or Option of one of those). For POST, PUT and PATCH, at most one parameter is not in the path, and it must be a record type, sent as the JSON body. Any other shape is A001, with a message naming the allowed form.
- Output: a wire type T, or Result[T, E] where E is a sum type. Wire types are defined under Code generation.
- HTTP mapping:
  - a value or `Ok(v)` returns status 200 with v as JSON;
  - `Err(e)` returns 400 with `{"error": e}`, where e carries a kind field naming its variant;
  - a failed requires or a malformed body returns 422 with `{"error": {"kind": "ValidationError", "rule": "<the failed clause in canonical text>"}}`;
  - a trap returns 500 with `{"error": {"kind": "InternalError"}}`, and the trap details go to the server log only.
- Two endpoints with the same method and path are A002.
- Canon-Py: an `@api("POST", "/todos")` decorator, next to `@requires`.

### Validation written once

- An api fn's `requires` is its request validation. The server enforces it (422), and the generated client checks it before sending.
- It must be portable, because it compiles to both Python and TypeScript. It may use comparisons, arithmetic, `&&`, `||`, `!`, field access, `str_len`, `trim`, `contains`, `len`, `is_email`, `is_some` and literals. Anything else in an api fn's requires is A003, which names the offending call.
- `ensures` is checked on the server only.

### Tables

```
table todos: Todo key id
```

A top-level declaration of a table of records, keyed by one field of type Int or String. These std.store built-ins operate on it, and each requires the effect `store(<table>)`:

| Built-in | Signature | Behavior |
| --- | --- | --- |
| get | `(t, key) -> Option[T]` | The row with that key, if any |
| scan | `(t) -> List[T]` | All rows, in insertion order (filtering happens in memory) |
| insert | `(t, row) -> Unit` | Adds a row; a duplicate key traps with R007 |
| save | `(t, row) -> T` | Inserts or replaces by key, and returns the row |
| delete | `(t, key) -> Bool` | Removes the row; true if one existed |
| next_id | `(t) -> Int` | One more than the largest Int key, or 1 for an empty table |
| count | `(t) -> Int` | The number of rows |

Under canon run and canon test, tables live in memory and start empty for every test. The generated Python stores them in SQLite.

### Effects with arguments

- `store(todos)` names the tables a function touches. The existing exact-effects rules (E101, E102) apply per table.
- `net(api.stripe.com)` names the hosts a function may call. A literal URL must use a declared host, or it's E104 at compile time *(amended)*. A computed URL is checked by the run-time capability guard, which traps with R006 on an undeclared host.
- Plain `net` (any host) remains legal, but the manifest flags it with warning W010.
- Canon-Py: `@effects("store(todos)", "net(api.stripe.com)")`.

### New built-ins

| Built-in | Signature | Effect |
| --- | --- | --- |
| is_email | `(s: String) -> Bool` | pure |
| uuid | `() -> String` | rand |
| hash_password | `(p: String) -> String` | rand |
| verify_password | `(p: String, hash: String) -> Bool` | pure |

New codes: A001 to A003 (api shape, route conflict, non-portable validation), M002 and M003 (modules), E104 (undeclared host) *(amended)*, R007 (duplicate key), W010 (any-host network).

## Worked example

One Canon file with three endpoints, and the files it compiles to. This is the golden output for M3 and M4: the implementer may improve it, but the generated code must stay at least this readable. Canon examples are illustrative until canon fmt formats them.

### The Canon source: canon/todos.cn

```
table todos: Todo key id

type Todo {
  id: Int,
  title: String,
  done: Bool,
}

type NewTodo {
  title: String,
}

type TodoError =
  | NotFound(id: Int)

api fn create_todo(input: NewTodo) -> Todo
  route: POST "/todos"
  effects: store(todos)
  requires: str_len(trim(input.title)) > 0
{
  let todo = Todo { id: next_id(todos), title: trim(input.title), done: false }
  insert(todos, todo)
  return todo
}

api fn complete_todo(id: Int) -> Result[Todo, TodoError]
  route: POST "/todos/{id}/complete"
  effects: store(todos)
{
  return match get(todos, id) {
    Some(t) => Ok(save(todos, Todo { id: t.id, title: t.title, done: true })),
    None => Err(NotFound(id)),
  }
}

api fn list_todos(page: Int, per_page: Int) -> List[Todo]
  route: GET "/todos"
  effects: store(todos)
  requires: page >= 1 && per_page >= 1 && per_page <= 100
{
  return todos
    |> scan()
    |> sort_by(|t| t.id)
    |> drop((page - 1) * per_page)
    |> take(per_page)
}
```

### Generated Python: backend/canon_generated/models.py

```python
# Generated by Canon 0.5.0 from canon/todos.cn. Do not edit: change the Canon source.
# canon-hash: sha256:3f9a0c...
from typing import Literal

from pydantic import BaseModel

from .runtime import SafeInt


class Todo(BaseModel):
    id: SafeInt
    title: str
    done: bool


class NewTodo(BaseModel):
    title: str


class NotFound(BaseModel):
    kind: Literal["NotFound"] = "NotFound"
    id: SafeInt


TodoError = NotFound
```

### Generated Python: backend/canon_generated/logic.py

Every effect becomes an explicit parameter, so the Python keeps Canon's permissions visible: create_todo can touch the todos table because it is handed that table, and nothing else.

```python
# Generated by Canon 0.5.0 from canon/todos.cn. Do not edit: change the Canon source.
from .models import NewTodo, NotFound, Todo, TodoError
from .runtime import Err, Ok, Result, Table, trim


def create_todo(input: NewTodo, todos: Table[Todo]) -> Todo:
    todo = Todo(id=todos.next_id(), title=trim(input.title), done=False)
    todos.insert(todo)
    return todo


def complete_todo(id: int, todos: Table[Todo]) -> Result[Todo, TodoError]:
    match todos.get(id):
        case Todo() as t:
            return Ok(todos.save(Todo(id=t.id, title=t.title, done=True)))
        case None:
            return Err(NotFound(id=id))


def list_todos(page: int, per_page: int, todos: Table[Todo]) -> list[Todo]:
    rows = sorted(todos.scan(), key=lambda t: t.id)
    start = (page - 1) * per_page
    return rows[start : start + per_page]
```

### Generated Python: backend/canon_generated/api.py

```python
# Generated by Canon 0.5.0 from canon/todos.cn. Do not edit: change the Canon source.
from typing import Annotated

from fastapi import APIRouter, Depends

from . import logic
from .models import NewTodo, Todo
from .runtime import Table, require, respond, table, trim

router = APIRouter()

Todos = Annotated[Table[Todo], Depends(table("todos", Todo))]


@router.post("/todos")
def create_todo(input: NewTodo, todos: Todos) -> Todo:
    require(len(trim(input.title)) > 0, "str_len(trim(input.title)) > 0")
    return logic.create_todo(input, todos)


@router.post("/todos/{id}/complete")
def complete_todo(id: int, todos: Todos) -> Todo:
    return respond(logic.complete_todo(id, todos))


@router.get("/todos")
def list_todos(page: int, per_page: int, todos: Todos) -> list[Todo]:
    require(
        page >= 1 and per_page >= 1 and per_page <= 100,
        "page >= 1 && per_page >= 1 && per_page <= 100",
    )
    return logic.list_todos(page, per_page, todos)
```

```ts
// Generated by Canon 0.5.0 from canon/todos.cn. Do not edit: change the Canon source.
import { strLen, trim, type ValidationError } from "./runtime";
import type { NewTodo } from "./types";

export function validateCreateTodo(input: NewTodo): ValidationError | null {
  if (!(strLen(trim(input.title)) > 0)) {
    return { kind: "ValidationError", rule: "str_len(trim(input.title)) > 0" };
  }
  return null;
}

export function validateListTodos(page: number, perPage: number): ValidationError | null {
  if (!(page >= 1 && perPage >= 1 && perPage <= 100)) {
    return { kind: "ValidationError", rule: "page >= 1 && per_page >= 1 && per_page <= 100" };
  }
  return null;
}
```

### Generated TypeScript: frontend/src/canon/client.ts

```ts
// Generated by Canon 0.5.0 from canon/todos.cn. Do not edit: change the Canon source.
import { request, type Result, type TransportError, type ValidationError } from "./runtime";
import type { NewTodo, Todo, TodoError } from "./types";
import { validateCreateTodo, validateListTodos } from "./validate";

export function createClient(baseUrl: string) {
  return {
    async createTodo(input: NewTodo): Promise<Result<Todo, ValidationError | TransportError>> {
      const invalid = validateCreateTodo(input);
      if (invalid) return { ok: false, error: invalid };
      return request(baseUrl, "POST", "/todos", { body: input });
    },

    async completeTodo(id: number): Promise<Result<Todo, TodoError | TransportError>> {
      return request(baseUrl, "POST", `/todos/${id}/complete`);
    },

    async listTodos(
      page: number,
      perPage: number,
    ): Promise<Result<Todo[], ValidationError | TransportError>> {
      const invalid = validateListTodos(page, perPage);
      if (invalid) return { ok: false, error: invalid };
      return request(baseUrl, "GET", "/todos", { query: { page, per_page: perPage } });
    },
  };
}
```

## Code generation rules

Generated code has two jobs: behave exactly like the Canon it came from, and read like a careful human wrote it. The worked example's Python already runs under FastAPI and passes mypy --strict against a stub runtime; the rules below keep every generated file to that standard.

### Wire format

The wire format is JSON, and it is the same on both sides by construction.

| Canon | JSON | Python | TypeScript |
| --- | --- | --- | --- |
| Int | number within ±(2^53 − 1) | SafeInt (an int bounded by Pydantic) | number |
| Float | number | float | number |
| Bool, String | boolean, string | bool, str | boolean, string |
| Unit | null | None | null |
| Option[T] | value or null | T \| None | T \| null |
| List[T] | array | list[T] | T[] |
| (A, B) | two-element array | tuple[A, B] | [A, B] |
| Map[String, V] | object | dict[str, V] | Record<string, V> |
| record | object with the record's fields | Pydantic BaseModel | interface |
| sum type | object with a kind field naming the variant, plus its fields | one model per variant with a Literal kind, joined by a discriminated union | union of object types on kind |

Function values, tables and maps with non-String keys are not wire types. Using one in an api fn signature is A001.

### Naming

- Field names are identical everywhere: in Canon, in JSON, in Python and in TypeScript. No case conversion on the wire, because conversion is exactly where mismatch bugs come from.
- Function and parameter names follow each language's style: create_todo in Python, createTodo in TypeScript. They never cross the wire. Query keys keep the Canon spelling (per_page).
- Type and variant names are unchanged.

### Python target

- Layout: canon_generated/ holds models.py, logic.py, store.py, api.py and a small runtime.py, plus one module per Canon module where a project has several. A user-owned main.py that creates the FastAPI app and includes the router is written once if missing, and never overwritten.
- Requirements: Python 3.11 or later, Pydantic v2, FastAPI. Storage uses the standard library's sqlite3, one table per Canon table, with records serialized by Pydantic.
- Effects become parameters. Each table a function touches is passed in as a `Table[T]`; each allowed host arrives as an HTTP client bound to that host. In the routes they are supplied with FastAPI dependencies. A generated function can only reach what it was handed.
- Errors: Result is the runtime's Ok / Err pair, and match statements unpack it. `respond` turns Err into a 400. `require` turns a failed check into a 422. The runtime installs an exception handler so error bodies are `{"error": ...}`, not FastAPI's default `{"detail": ...}`.
- Contracts: requires on an api fn becomes a `require(...)` call at the top of the route. Other contracts become runtime checks inside the logic function, raising the same traps as the JavaScript runtime.

### TypeScript target

- Layout: frontend/src/canon/ holds types.ts, validate.ts, client.ts and a small runtime.ts. No dependencies: the client uses fetch.
- `createClient(baseUrl, options?)` returns one async method per api fn. Each returns `Result<T, E | ValidationError | TransportError>`, where TransportError covers network failures and 500s. Methods never throw.
- Validators run first: a method whose endpoint has requires calls its generated validator before any request is sent.

### Semantic parity

The same expression must mean the same thing in all three places. Where the host language differs from Canon, generated code calls a runtime helper instead of the native operator:

| Canon | Python pitfall | TypeScript pitfall | Rule |
| --- | --- | --- | --- |
| Int division `/` | `//` floors toward negative infinity | `/` gives a float | helper `div`, truncating toward zero |
| `str_len(s)` | `len` counts code points (same) | `.length` counts UTF-16 units | TypeScript uses `strLen`, counting code points |
| `trim(s)` | `strip` treats more characters as whitespace | `trim` differs from Python | helper `trim` in both, with one shared definition of whitespace |
| Int overflow | integers never overflow | precision is lost silently | values on the wire are range-checked (SafeInt); logic traps with R003 |
| `sort_by` | `sorted` is stable (same) | `sort` is stable in ES2019 and later (same) | native, with a key function |

The parity suite: generate 2,000 random expressions from the portable subset, evaluate each in the JavaScript runtime, the generated Python and the generated TypeScript, and require identical results. Run it in CI.

### Readability bar

- Linters and checkers: Python passes ruff check, ruff format --check and mypy --strict. TypeScript passes tsc --strict, prettier --check and eslint.
- One-to-one mapping: each Canon function becomes one function with the same name (in the target's case style), in the same order. A Canon comment above a function becomes a docstring or JSDoc comment.
- No clever code: no metaprogramming, no generated helper soup. The runtime files stay under 250 lines each.
- Golden files: the worked example and every program in examples/ have committed expected outputs, and CI diffs against them.

### Read-only output

- Header: every generated file starts with "Generated by Canon ... Do not edit: change the Canon source," plus a hash of its own contents.
- Drift protection: canon check fails with G001 when a generated file's hash no longer matches its contents, naming the file and the Canon source to edit instead. canon build refuses to overwrite an edited file unless given `--force`.
- User-owned files (main.py, the React app) are never touched after creation.

## Toolchain

One config file and four commands cover the full-stack workflow; every command keeps `--json` output for agents.

### canon.toml

```toml
[project]
name = "todos"
src = "canon"

[backend]
target = "fastapi"
out = "backend/canon_generated"

[frontend]
target = "ts-client"
out = "frontend/src/canon"
```

### Commands

| Command | What it does |
| --- | --- |
| canon check | Checks the whole project: every module, imports, api fn shapes, effects, validation portability, and generated-file drift (G001). Patches as today. |
| canon build | Generates the backend and frontend outputs named in canon.toml. Refuses to overwrite hand-edited generated files without `--force`. `--target fastapi` or `--target ts-client` builds one side. |
| canon dev | `canon build --watch`, plus the backend served with `uvicorn --reload`, for local development. |
| canon manifest | Lists every endpoint: method, path, function, effects (tables and hosts), and validation rules. Text for people, `--json` for policies and agents. |
| canon test | Runs test blocks across the project, with in-memory tables that start empty for each test. |

### Agent loop

An agent working in a Canon project needs exactly one command after each edit: `canon check --json`. It applies every fix.diff, repeats until the project is clean, then runs `canon build`. The full-stack addendum to the agent reference (M7) teaches this loop.

## Experiment FS-1

FS-1 asks one question: do agents ship more working full-stack features, with fewer frontend–backend mismatches, when they write Canon than when they write Python and TypeScript directly?

### Three arms, one app

Every arm starts from the same small app, "shop" (users, products, orders), implemented three ways that pass one shared hidden test suite.

| Arm | What the agent edits | Checks it can run |
| --- | --- | --- |
| A. Direct | FastAPI backend, TypeScript types and client, by hand | mypy --strict, ruff (fixes applied automatically), tsc, eslint --fix, the starter's visible tests |
| B. Direct + OpenAPI | FastAPI backend by hand; TypeScript types and client generated from FastAPI's OpenAPI schema by a build command | the same as A, plus the generator |
| C. Canon | Canon source; canon build generates both sides | canon check --json (fixes applied automatically), canon test, the starter's visible tests |

Arm B is the one that matters. Generating a TypeScript client from a backend's schema is how careful teams already keep the two sides in sync. Any reviewer will ask "why not just use OpenAPI codegen?", and FS-1 answers it with data. Against B, Canon's edge has to come from more than shared types: validation written once, typed errors, and effects.

### Tasks

- 40 feature tasks: each adds an endpoint, the client call and a small frontend module that uses it. Examples: "add order cancellation," "paginate the product list," "let a user change their display name."
- 20 change tasks: each changes something that both sides depend on. Examples: rename a field everywhere, add a required field with a validation rule, change a field's type, split one endpoint into two.
- Hidden tests for every task:
  - HTTP tests against the backend;
  - client tests, in which the frontend module calls the client against the running server;
  - boundary probes, which check that the server accepts what the client sends and the client parses what the server returns;
  - the full regression suite.
- Verified first: every task has a reference solution in all three arms that passes all of its hidden tests.

### Procedure

- Same scaffold for every model: read a file, write a file, run an allowed command.
- Same budget: up to 5 edit-and-check rounds per task. Agents see check output and visible tests, never the hidden tests.
- Same prompt template in every arm, with the same output instruction. The Canon arm also gets the core reference and the full-stack addendum, and those tokens count toward its cost.
- Models: Qwen2.5-Coder 7B (local), Claude Opus 5.5 and GPT-6.2 Sol. If the pilot shows Qwen passing under 10% of tasks in every arm, Qwen is reported as exploratory.

### Metrics

| Metric | Definition |
| --- | --- |
| End-to-end pass rate (primary) | Share of runs where every hidden test for the task passes, with no regressions |
| Mismatch rate | Share of runs with at least one failed boundary probe |
| Change-task success | End-to-end pass rate on the 20 change tasks |
| Validation agreement | On 1,000 random inputs per endpoint, how often client and server agree on what's valid |
| False acceptance | Share of runs where the arm's own checks pass but hidden tests fail |
| Effort and cost | Tokens, rounds and wall time per passing task; dollars for API models |

### Analysis and pre-registration

- Unit of analysis: the task. Runs are paired by task across arms, with 95% bootstrap intervals over tasks.
- Primary comparison: Canon against the better of A and B on end-to-end pass rate, per frontier model. The baseline is chosen from the pilot, before the main run.
- Outcomes: win, non-inferior, inconclusive or lose. The non-inferiority margin comes from a power analysis on the pilot and is written down before the main run.
- Predictions, recorded with the pre-registration, including where Canon should lose:
  - feature tasks: Canon roughly ties both baselines;
  - change tasks and mismatch rate: Canon beats A clearly, and beats B by less;
  - validation agreement: Canon beats both, because only Canon writes validation once;
  - cost: Canon uses more tokens, because of the reference.
- The win rule for "Canon is the better full-stack language for agents": for both frontier models, Canon is non-inferior to the chosen baseline on end-to-end pass rate, and significantly better on change-task success or mismatch rate.
- Locked in the pre-registration: prompts, temperature, model and tool versions, the scaffold, the rule for rerunning infrastructure failures (rerun crashes and timeouts, never wrong answers), and the analysis script, tested on pilot data.
- Size: set by the power analysis. As a starting estimate, 60 tasks × 3 arms × 3 models × 3 runs is 1,620 runs, with a dollar cap on the API models fixed before the run.

## Risks and open questions

The biggest risk is the one FS-1 exists to test: models know Python and TypeScript far better than Canon, and that familiarity may outweigh everything Canon's structure adds.

| Risk | Why it matters | Mitigation |
| --- | --- | --- |
| Unfamiliar language | Models have seen billions of lines of Python and TypeScript and none of Canon | FS-1 measures it directly; the Canon-Py surface is available if Experiment 1 favors it |
| The OpenAPI baseline closes the gap | Arm B already keeps types in sync, so mismatch wins could shrink | Canon's remaining edge is validation written once, typed errors and effects; validation agreement measures the first |
| Generated code looks machine-made | Developers reject output they can't read and maintain | The readability bar, golden files and linters in CI; review the worked example's output before building anything else |
| Humans edit generated files | Edits get lost, or Canon and the code drift apart | Read-only headers, G001, and build refusing to overwrite; user-owned files stay separate |
| Semantics differ across three runtimes | A rule that passes in the client and fails on the server is a new class of mismatch | The portable subset, runtime helpers, and the parity suite in CI |
| The reference outgrows its budget | Every token of reference is paid on every request | Core reference under 4,000 tokens; addendum under 1,500; measured in CI |
| Scope creep | Auth, migrations and queries each look small and aren't | Out of scope in v0.5, by name; each needs its own design |
| The Wasp lesson | Wasp dropped its own full-stack language because AI tools didn't know it | Canon is written for agents and ships its reference in every prompt; FS-1 tests whether that's enough |

Open questions for after FS-1: custom HTTP status codes per error variant; read and write effects per table (`reads(users)` versus `writes(users)`); indexed queries; generating Pydantic or Zod validators instead of hand-written checks; whether to generate a React hooks layer on top of the client.

## How this fits the roadmap

- v0.5 is now "full-stack." The earlier v0.5 plan in docs/roadmap-to-1.0.md (proven contracts, synthesis, a library of proven functions) moves later. Record the change in DECISIONS.md.
- Experiment 1's harness is already built, and its local runs cost nothing. Run it overnight before FS-1: it settles whether Canon-Py becomes the default, and FS-1's Canon arm should use whichever surface wins.
- FS-1's result decides what comes next. A win makes the full-stack direction Canon's main story. A tie against arm B (OpenAPI) means the next version has to widen the gap beyond shared types.
