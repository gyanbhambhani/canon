2026-11-22. Status: implemented on branch `worktree-agent-ab1aef41ad941f802` for review; **not
benchmarked**. No model API was called to write this. Every number below comes from data already in

## Summary

- **The measurement that decides the design** says the largest lever is not any construct but the
  syntax family. Under both Qwen models, a strict, effect-typed subset of Python syntax ("Canon-Py")
  is as natural as plain typed Python, and 14 to 17 nats per program less surprising than Canon's
  own syntax even when Canon is conditioned on its full reference and Canon-Py only on a much
  shorter rules page. No piecemeal edit to Canon's syntax closes that gap; most make it worse.
- **What v0.3 builds** is the part the evidence supports and that can be made solid now: a
  self-healing toolchain (every recorded first-draft failure was mechanical, and a replay shows
  `--fix` would have made all of them valid with their hidden tests passing), contract fuzzing,
  sealed effects with a run-time guard, three model-preferred spellings, and ranked suggestions for
  type errors. Each has a switch for ablation.
- **What v0.3 recommends but does not build** is Canon-Py, staged behind a cheap pre-registered
  test (Experiment D), because the evidence for it is a proxy (base-model surprisal), not agent
  behaviour.
- **Where Python still wins** after v0.3: everywhere on surprisal (by 19 to 38 nats per program
  with the reference) and on code length (Canon programs average 88 to 101 Qwen tokens, typed
  Python 60). v0.3 does not change those numbers; it is token-neutral by design.

## The measurement that decides the design

The owner's objective for v0.3 is that Canon be the language an agent has to think least about. The
proxy measured here is **total surprisal of a correct program**: the negative log-likelihood, in
nats, summed over its tokens under a local base code model. It combines length (more tokens, more
nats) and familiarity (confident tokens cost little). It is a proxy: it says how natural the text is
to a code model, not how often an agent writes it correctly.

Setup (research/v0.3/surprisal, `score.py` and `analyze.py`): all 50 benchmark tasks; Canon v0.2 and
TypeScript are the modal (most frequent) final program per task and model from the v0.2 benchmark,
all of which passed the hidden tests; typed Python and Canon-Py were written by hand and pass the
same tests (166 cases, 0 failures). Qwen2.5-Coder-1.5B (fp32) and 7B (fp16). 95% bootstrap intervals
over tasks (10,000 resamples, seed 2026). "Bare" means a one-line header (`# Canon`, `# Python`, ...);
"with reference" means Canon is conditioned on the For agents page, only program tokens counted.

| Program set (mean per program) | Surprisal, 1.5B (nats) | Surprisal, 7B | Qwen tokens | Nats per token, 1.5B / 7B |
| --- | ---: | ---: | ---: | ---: |

| Canon v0.2, Claude's programs, with reference | 70.5 [58, 86] | 62.1 [51, 75] | 87.9 | 0.80 / 0.71 |

Paired differences (per task, A minus B):

- Canon (Claude, with reference) minus Python: +25 [16, 35] nats (1.5B), +19 [12, 28] (7B).
- The reference lowers Canon's surprisal by 38 to 41 nats per program, about 37%: the reference is
  doing real work, and an agent should always have it.
- Canon-Py minus Python: +0.2 [-2.1, 2.1] (1.5B), +1.8 [0.1, 3.2] (7B). Canon's restrictions, spelled
  in Python, cost almost nothing.
- Controlling for the algorithm (20 tasks; Claude's Canon programs transliterated to Canon-Py with
  the same helpers and names): Canon-Py is lower by 51 nats (1.5B) and 46 (7B) bare, and by 17
  [7, 27] and 14 [4, 22] when each language gets its own documentation as prefix.
- Candidate edits to Canon's own syntax, applied textually to the same programs (bare, mean over 50
  tasks; negative is better): indentation instead of braces +2 to +5; `fn f() -> T = e` +1.5 to
  +2.4; dropping `let` +0.7 to +1.3; implicit final return about 0; all edits together +5 to +9;
  `&&`/`||`/`!` about -0.2 (-1.4 to -2.0 per program it touches, Claude's programs only);
  `for (i, x) in enumerate(xs)` -0.4 to -0.7 (-5 to -8 per program it touches, but only 4 programs).

Two readings follow.

1. **Familiarity dominates length, and it is decided at the level of the syntax family.** Every
   "make Canon terser" edit produced a hybrid (`fn f(x: Int) -> Int:`) that the models find less
   natural than either parent. The one surface that is both shorter and natural is Python's.
2. **Most of an agent's cost is not code.** In the v0.2 benchmark Claude's Canon answers averaged
   427 output tokens on first pass, of which about 87 are code (Qwen tokenizer as a proxy; about
   20%), against 237 and about 117 (49%) for TypeScript ([tokens/RESULTS.md](../research/v0.3/tokens/RESULTS.md)
   section 4). The full set of terse edits would save about 10 code tokens, 2% of Claude's output.
   The remaining 200-odd extra tokens are reasoning. The surprisal gap is the best available
   predictor of that reasoning, which is why familiarity, not brevity, is the objective; but the
   link between base-model surprisal and an instruction model's reasoning length is a hypothesis,
   and Experiment D2 in the pre-registration is the cheapest test of it.

## The six problems

Each section gives the evidence, the change, why it should help, what it costs, and how the
pre-registered experiment would test it.

### 1. No early loop exit

**Evidence.** In v0, `apply_ops` with Claude produced 10 distinct Canon programs against 1 TypeScript
program (REPORT.md, distinct-programs table), and the exploratory analysis attributes this to the
missing `break` and the `match` restriction. The v0.2 data changes the picture: with `match` allowed
everywhere (v0.2), Claude's `apply_ops` variants all use an early `return` from inside the loop; they
differ in how they test a variant (a `match` to Bool, a helper, a `try` step function) and in
`pair.0`/`pair.1` from `enumerate` (62 of 1,000 v0.2 Canon programs use enumerate with slot access).
Flag variables for loop exit appear in only 10 of 1,000 v0.2 Canon programs (6 in
`balanced_parens`), while 48 of 1,000 TypeScript programs use `break` (rpn 16, apply_ops 10,
total_area 10) and 26 use `continue`. Likelihood (REPORT-v0.3.md, `early-exit`): a done-flag never
wins; `break` wins in 2 of 3 contexts for both models (early `return` wins the third, where it is
simply shorter). `continue` loses to a negated `if` guard in every context for both models (9 to 23
times less likely).

**Change (adopted).** `break`, alone on its line, leaves the innermost loop; T010 outside a loop.
No `continue`. No `find`/`first_where` library function: `return` from a loop already covers
"find", and a second way to search would add variants. Also adopted: `for (i, x) in xs` destructuring,
the one candidate edit with a clear surprisal win per program it touches (-5 to -8 nats) and a strong
likelihood win (0.010 to 0.017 times as likely to write `p.0`/`p.1`, 2/3 and 3/3 contexts).

**Cost.** Two statements' worth of reference text (about 60 tokens). `break` makes "flag variable
plus condition" and "break" two ways to stop a `while`; models already prefer `break`, so this trades
a rare improvised form for a common native one. Destructuring leaves `for p in enumerate(xs)` legal,
so it adds a second way to read a tuple in a loop; fmt cannot rewrite one into the other without
inventing names. `break` is contextual (not reserved), so no v0.2 program breaks.

**Test.** Experiment A, H4 and H5d, with the `canon-v0.3-v02syntax` arm as the ablation. Expected:
no detectable change in distinct programs; the evidence above says early exit was a v0 problem that
v0.2's `match` change mostly solved.

### 2. Self-inflicted first-draft failures

**Evidence.** Every failed Canon first draft in both benchmarks failed only on mechanical codes:
v0 19 of 500 (Claude) and 35 of 500 (GPT-6.2 Sol), v0.2 11 and 50; codes C001 and L001 only (one
P005 in v0). Reading the v0.2 failures: 30 of 61 are the pipeline rule (`return join(reverse(split(s, " ")), " ")`
must be a pipeline), 9 are redundant parentheses or a statement split across lines
(`(k / 2) * (k + 1)`), 2 are `try match` needing parentheses, 12 include L001, almost all a long list
literal (`validate_user`), and 8 are whitespace or a pipeline inside an expression
(classified from each draft's diff to its fixed version; research/v0.3/replay is the authoritative count of what `--fix` repairs).

**Change (adopted, rank 1).** `canon check --fix` applies C001, E101, E102 and T009 patches one at
a time, re-checking after each, until none remains, and returns only what needs judgment (never
T004, whose patch inserts holes). To make L001 mechanical, fmt now breaks a statement longer than 100
characters at its outermost list, tuple, record or call brackets, one item per line with a trailing
comma, the form models already wrote in those drafts. Design law 1 holds: what is stored and accepted
is still exactly fmt's output.

**Retrospective replay** (research/v0.3/replay, no model calls): applying `fix()` to every recorded
Canon first draft.

| Run | Model | First-pass valid (recorded) | After `--fix`, v0.2 language | After `--fix`, v0.3 | Fixed drafts passing all hidden tests | Clean drafts broken |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| v0.2 | claude-opus-5-5 | 97.8% | 98.8% | 100.0% | 11 of 11 | 0 |
| v0.2 | gpt-6.2-sol | 90.0% | 98.8% | 100.0% | 50 of 50 | 0 |
| v0 | claude-opus-5-5 | 96.2% | 98.8% | 99.8% | 18 of 18 | 0 |
| v0 | gpt-6.2-sol | 93.0% | 99.0% | 100.0% | 35 of 35 | 0 |

The difference between the two `--fix` columns is the line-wrapping rule.

**Why it should help.** The agent never spends a turn on layout, so turns to correct should reach
TypeScript's 1.00 and first-try validity TypeScript's 100%.

**Cost.** None in the reference beyond one sentence. The caveat is that the replay assumes the model
writes the same draft; an agent told that the toolchain fixes layout might write differently (better
or worse). Wrapping adds one canonical-form rule.

**Test.** Experiment A, H1 and H1a (the `canon-v0.3-nofix` arm isolates the loop).

### 3. Cost

**Evidence.** Claude's dollars per correct program: $0.0105 Canon v0.2 against $0.0054 TypeScript,
1.92x (REPORT-v0.2.md, C6 not supported). About 86% of a Canon run's cost is output. Output tokens:
Claude 451 against 237, GPT-6.2 Sol 192 against 125. The code itself is not the reason: Claude's
Canon programs are shorter than its TypeScript (87.9 against 110.6 Qwen tokens), and the code share
of Claude's Canon output is about 20% against 49% for TypeScript (tokens/RESULTS.md).

**Change.** No syntax change can recover this; the measurement above shows terse edits save about
2% of output and raise surprisal. v0.3's contribution is indirect: `--fix` removes fix rounds
(2 to 10% of runs) and one class of thing to remember. The structural fix is the familiarity of the
surface: see "Strategic option: Canon-Py" below.

Where tokens go that Python does not spend (tokens/RESULTS.md section 2, average of both models'
programs): closing-brace lines +6.6 per program, helper headers +4.6 (0.4 helpers per Canon program
against 0.04 in Python), indentation +4.0, requires/ensures +2.6, signature types +1.8, `let`/`var`
+1.8; and a residual of +21 that is not syntax at all but missing capability: no indexing or slicing,
no character tests or string repeat, hand-written integer parsing (`parse_sum` 248 tokens against 52),
and 53-bit Int caution (GPT's `collatz_steps` 404 tokens against 64). The residual points at the
standard library (problem 4 and the v0.4 list), not at grammar.

**Test.** Experiment A, H2, H3 and H3p, stated in advance as likely not supported.

### 4. Consistency did not improve

**Evidence.** C3 not supported in v0 or v0.2 (ratios 1.04 to 1.20 against TypeScript); D1 (v0.2
better than v0) not supported (0.98 and 1.02). Ignoring identifier names barely changes the counts
(REPORT.md: 3.48 and 3.16 against 3.70 and 3.30), so naming is not the whole story; reading the
variants shows decomposition (whether and how to factor a helper), optional contracts, and the
workarounds above.

**Change.** None claimed. No grammar fixes how a model decomposes a problem or names a helper. Two
v0.3 changes remove specific variant sources (`pair.0` versus `let i = p.0`, flags versus `break`),
and a fuller standard library would remove the hand-written workarounds that differ run to run; that
is deferred to v0.4 because each function added is reference text and needs its own evidence.

**Test.** Experiment A, H5 and H5d, expected not supported. If H5d is not supported again, the
convergence claim should be dropped from Canon's pitch, not re-tested a third time with small changes.

### 5. First-try validity below TypeScript's

**Evidence.** 90.0 to 97.8% against 100% (REPORT-v0.2.md). All failures mechanical (problem 2).

**Change.** The same as problem 2. In the replay, v0.3 with `--fix` reaches 100.0% for both models
on the v0.2 drafts. This is the one place the data says v0.3 should match TypeScript outright.

**Test.** Experiment A, H1; Experiment B, B1 and B4 for weaker models, where first drafts fail more.

### 6. Test blocks were not effect-checked

**Evidence.** DECISIONS.md (M5) documented that a `test` block may perform any effect. A red-team
pass for v0.3 (tests/effects, 17 programs) found a second hole: a `requires` or `ensures` clause could
call `now()`, `random()` or any effectful user function, invisible in every signature. Every other
attempt (function values passed to `map`, lambdas stored in records and lists, `Some(now)`, a match
returning `random`, a generic identity on `print`, local aliases, three-deep chains) was already
caught by E101, because Canon attributes an effect to the function that names the effectful function.

**Change (adopted).** Sealed effects: test blocks are effect-checked; `fs` and `net` are declared
with an `effects:` line after the test name; `io`, `time` and `rand` are not, because the test host
makes them deterministic (the likelihood study found a clause on a test 21 to 112 times less likely
than none, so the common case stays clause-free). Contracts must be pure (E103). At run time the
host performs only the effects the entry point declares (main's clause; a test's fs/net plus the
virtual three; none during fuzzing); the checker makes this unreachable, and a test forges a compiled
module to show the guard still stops it.

**What the claim is, exactly.** "The effects a checked program can perform are bounded by `main`'s
signature; a test's by its own." It is not "every function's effects are in its own signature": a
pure-looking `fn apply(f: fn(String) -> Unit, s: String)` performs io when given `print`; the caller
that names `print` must declare io. Effect annotations on function types (`fn(String) -> io Unit`)
would make each signature exact; the likelihood study split on the spelling (the 1.5B model prefers
a trailing clause, the 7B `-> io B`), and it adds effect polymorphism to the type checker. Deferred
to v0.4.

**Cost.** Two codes (E103 and test E101/E102) and about 40 tokens of reference. A v0.2 test that
uses fs or net needs one line; `canon check --fix --write` adds it.

**Test.** Experiment C (deterministic red team, plus an independent red team before the claim is
published), and the cost check in Experiment A.

## Strategic option: Canon-Py

**What it is** (prototype rules: [canonpy/RULES.md](../research/v0.3/canonpy/RULES.md); 50 idiomatic
programs and 20 transliterations, all passing the tests). Typed Python 3.12 syntax with Canon's
rules: every `def` fully annotated, locals never; one Black-style canonical layout; effects as an
`@effects(io, fs)` decorator, pure when absent; `@requires(...)`/`@ensures(...)`; `Result[T, E]` with
`Ok`/`Err` and `try_(e)` propagation; `T | None` for Option; exhaustive `match`/`case`; sum types on
one `type Op = Deposit(amount: int) | Withdraw(amount: int)` line; no imports, truthiness, generator
expressions or classes with methods; a closed set of str/list/dict methods; indexing and slicing.

**What the evidence says.** About as surprising as plain typed Python (within 2 nats) and far less
than Canon v0.2 (table above). Bare Canon-Py with no documentation ties Canon v0.2 with its whole
reference. The two choices inside it that were measured (`e?` against `try_(e)`; the compact `type`
line against dataclasses) make no difference.

**What it would cost to build,** staged so each stage is useful alone:

1. *Front end* (parser for the subset with an indentation lexer, canonical printer, the C001 and
   E101/E102 machinery): it maps onto the existing AST, so the checker, codegen and runtime are
   reused. Estimate: the size of the current lexer, parser and printer (about 1,000 lines) plus fuzz and
   conformance corpora. This alone is enough for Experiment D2.
2. *Semantics alignment*: Python's `int` is unbounded and its `/` is float division, Canon's Int is
   53-bit and truncates; `None` is a value, Canon's `None` is a variant. Choose per case and record it;
   the safest is Python's meaning everywhere a Python reader would assume it, with traps where Canon
   cannot match it (big ints).
3. *Migration*: a translator from Canon v0.3 ASTs to Canon-Py text (mechanical; the transliterations
   in canonpy/translit were made the same way by hand), and `canon fmt --to-py`.
4. *Retire or keep Canon syntax*: decided by Experiment A and D results, not now.

**Risks.** Python's surface brings Python's many ways (comprehension or loop, f-string or `+`, `+=`
or `x = x + 1`); the canonical form must pick one for each, and the likelihood study must be repeated
for those choices. The prototype allows parameter mutation (`balance += amount`) and f-strings, which
Canon forbids or lacks; each needs a ruling. A model that recognizes Python may write Python that is
outside the subset (imports, classes) more often; the checker must answer with patches, and the first
draft failure rate may rise before it falls. Constrained decoding (design law 6) is harder with
significant indentation; the law was chosen for that reason and would need revisiting, and v0.3's
measurement found braces preferred over indentation *within Canon's syntax* (2/3 contexts, 1.2 to 9
times), so the gain is not from indentation as such but from the whole family.

## Where Python still wins, after v0.3

- **Surprisal:** typed Python beats Canon v0.3 by the same 19 to 38 nats per program as v0.2 (v0.3's
  spelling changes move it by under 1 nat on average).
- **Length:** 59.7 Qwen tokens per program against 87.9 to 100.9 for Canon (v0.3 fmt changes Canon's
  token counts by -0.01% on the benchmark corpus: research/v0.3/tokens/V03_DELTA.md). Python's type
  hints cost it 9 tokens (15%); untyped Python is 50.7.
- **Standard library:** most of the length gap is capability (indexing, string helpers), not syntax.
- **What Canon has that Python lacks:** a checked effects boundary, exact effect lists, canonical
  text, patches for every mechanical error, a self-healing loop, exhaustive match, contracts checked by
  fuzzing. None of these is in tension with Python's syntax, which is the argument for Canon-Py.

## Ablation switches

Every v0.3 change can be turned off alone. Compiler options (`features` in `check`, `fmt`,
`compileJs`; defined in `packages/compiler/src/features.ts`) and CLI flags:

| Change | Compiler switch | CLI flag | Off means |
| --- | --- | --- | --- |
| Self-healing loop | (call `fix()` or not) | `check --fix` (opt-in) | the harness runs plain `check` |
| Line wrapping | `wrap` | `--no-wrap` | long lines stay, L001 |
| `break` | `break` | `--no-break` | `break` is a bare name (P004) |
| Destructuring | `destructure` | `--no-destructure` | `for (a, b) in` is a parse error |
| `&&` `||` `!` | `symbols` | `--no-symbols` | fmt prints `and`, `or`, `not` (both still parse) |
| Sealed effects | `sealedEffects` | `--no-sealed-effects` | tests and contracts are not effect-checked (v0.2) |
| Suggestions | `suggestions` | `--no-suggestions` | T001 has no `data.suggestions` |
| Capability guard | `RunOptions.capabilityGuard` | `--no-capability-guard` (run, test) | the host allows any effect not denied |
| Contract fuzzing | (call `fuzzContracts` or not) | `--no-contract-fuzz` (test) | `canon test` runs test blocks only |
| All language switches | `features: V02` | `--v0.2` | the v0.2 language, byte for byte on the conformance corpus |

## Reference budget

The For agents page grew from 7,187 to about 7,900 characters (about 2,260 tokens at 3.5 characters
per token, against the 4,000 budget). The additions are `&&`/`||`/`!`, `break`, destructuring, test
effects, E103/T010, `--fix`, fuzzing and one example function.

## What a reviewer is likely to push back on

- **Surprisal is a proxy.** Base Qwen models scoring hand-written programs say nothing directly about
  whether Claude or GPT write correct code faster. Experiment D2 is designed to be the cheap check.
- **The hand-written arms are idiomatic; the Canon arms are model output.** The 20-task
  transliteration controls for algorithm, and the effect survives it, but the 50-task comparison
  mixes style with syntax.
- **The replay is counterfactual.** It assumes the same drafts; a model told that layout fixes itself
  may write different code.
- **The headline v0.3 gains are toolchain, not language.** TypeScript with an auto-fix loop (Experiment
  1's `ts-patch`) gets some of the same benefit; Canon's advantage is that all of its first-draft
  failures were mechanical, which is a property of having a canonical form, but it is fair to ask
  whether that is a language result.
- **Fuzzing only checks what agents write down.** Models wrote contracts in about a quarter of Claude's
  programs and fewer of GPT-6.2 Sol's (13 and 9 of 50 modal programs); B5 makes "not testable" an
  explicit outcome.
- **Sealed effects is a program-level, not a function-level, guarantee** until function types carry
  effects.
