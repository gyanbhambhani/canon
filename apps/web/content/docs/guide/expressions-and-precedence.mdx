This page covers expressions: operator precedence, logic, arithmetic, strings, comparisons, calls and lambdas.

```canon
test "precedence" {
  assert(1 + 2 * 3 == 7)
  assert((1 + 2) * 3 == 9)
  assert(!(1 > 2))
  assert(false && 1 / 0 == 0 || true)
}
```

The last line shows that `&&` and `||` short-circuit: `1 / 0` is never evaluated.

## Precedence

Loosest first. Operators on one row associate to the left, except comparisons, which never chain.

| Binds | Operators |
|---|---|
| loosest | `\|>` pipeline, lambdas `\|a, b\| expr` |
| | `\|\|` (or) |
| | `&&` (and) |
| | `== != < <= > >=` (never chained) |
| | `+ -` |
| | `* / %` |
| | unary `-`, `!`, `try` |
| tightest | calls `f(x)`, fields `a.b`, tuple slots `t.0` |

Parentheses the precedence already implies are redundant, and the formatter removes them: `((a + 1)) > (2)` becomes `a + 1 > 2`.

## Logic: &&, || and !

`&&` and `||` take two Bools and short-circuit. `!` negates, and binds as tightly as unary minus, as in TypeScript and Rust: `!a == b` means `(!a) == b`, so negating a comparison needs parentheses, `!(a > b)`.

```canon
fn in_window(t: Int, lo: Int, hi: Int, closed: Bool) -> Bool {
  return !closed && t >= lo && t < hi || t == lo
}

test "logic" {
  assert(in_window(5, 0, 10, false))
  assert(!in_window(5, 0, 10, true))
  assert(!(3 > 4))
}
```

The formatter collapses comparisons with a Bool literal and double negation: `x == true` becomes `x`, `x == false` becomes `!x`, and `!!x` becomes `x`. `||` at the start of an expression is a lambda with no parameters (`|| 1`), as in Rust; between two operands it is "or".

v0.2 spelled these `and`, `or` and `not`, with `not` binding looser than comparison. The words still parse, and the formatter rewrites them to symbols, adding parentheses where the old `not` covered a comparison (`not a == b` becomes `!(a == b)`), so the meaning never changes. [Formatting rules](/docs/canonical-form#migrating-from-v02) shows the migration.

## Comparisons do not chain

`1 < a < 3` is a parse error (P001). Join two comparisons with `&&`.

```canon
# expect: P001
fn between(a: Int) -> Bool {
  return 1 < a < 3
}
```

```canon
fn between(a: Int) -> Bool {
  return 1 < a && a < 3
}
```

## Arithmetic

Int with Int gives Int, and Float with Float gives Float. Mixing them is T009, and its patch wraps the Int side in `to_float` (`canon check --fix` applies it). Int division truncates toward zero, and `%` takes the sign of the left side. Dividing by zero, or taking `%` of zero, traps with R004. An Int result outside the 53-bit safe range traps with R003.

```canon
test "integer arithmetic" {
  assert(7 / 2 == 3)
  assert(-7 / 2 == -3)
  assert(-7 % 2 == -1)
  assert(7.0 / 2.0 == 3.5)
}
```

```canon
# expect: T009
fn scale(n: Int, x: Float) -> Float {
  return n * x
}
```

The T009 patch restates the program; it does not guess. `sum(xs) / len(xs) * 1.0` becomes `to_float(sum(xs) / len(xs)) * 1.0`, which still divides Ints. For a Float average, convert both sides first: `to_float(sum(xs)) / to_float(len(xs))`.

## Joining strings

`+` also joins two Strings. Both sides must be String: `"n = " + 3` is T001, and its first suggested fix is `to_string(3)`. `-`, `*`, `/` and `%` are numeric only.

```canon
test "strings join with +" {
  let n = 3
  assert("a" + "b" + "c" == "abc")
  assert("n = " + to_string(n) == "n = 3")
}
```

## Comparison and equality

`<`, `<=`, `>` and `>=` work on Int, Float and String (strings compare by code point). `==` and `!=` compare any two values of the same type by structure: lists, tuples, records and variants included. Comparing values of different types is T001, and so is comparing functions.

## Calls, fields and tuple slots

Only named functions are called, and there are no methods. `len(xs)` is the only way to write a length; `xs.len()` is read as a call into a module named `xs` and rejected (T002). There is no indexing operator either: use `first`, `last`, `take`, `drop`, `enumerate` or `map_get`.

Fields are read with `a.b`, and tuple slots with `t.0`, `t.1`. A call's `(` must sit on the same line as the function name.

## Lambdas

A lambda is `|params| expr`, and its body is one expression. Parameter types come from the expected type at the call site, so lambdas never carry annotations.

```canon
fn bump_all(xs: List[Int], k: Int) -> List[Int] {
  return map(xs, |x| x + k)
}

test "lambdas" {
  assert(bump_all([1, 2], 10) == [11, 12])
  let add = |a, b| a + b
  assert(add(2, 3) == 5)
}
```

A lambda with n parameters that receives a single n-tuple unpacks it, which is how `map(pairs, |k, v| ...)` works. Lambdas capture values, never variables: a lambda that reads a `var` sees the value it had when the lambda was created.

```canon
test "tuple unpacking and capture" {
  let pairs = [("a", 1), ("b", 2)]
  assert(map(pairs, |name, n| n * 2) == [2, 4])
  var k = 1
  let add_k = |x| x + k
  k = 100
  assert(add_k(1) == 2)
}
```

`try` is not allowed inside a lambda (T007), because an early return from it would leave the lambda, not the function.

## Evaluation order

Evaluation is strict and left to right; arguments are evaluated before the call. `match` is an expression and may appear in any expression position, including as an operand or an argument; it binds like a call, so `(match a { … }) + 1` adds 1 to the match's value. See [Pattern matching](/docs/guide/pattern-matching).
