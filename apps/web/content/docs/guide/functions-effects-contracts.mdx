This page covers functions: typed signatures, the `effects` clause that lists a function's side effects, contracts that check inputs and outputs, and what a checked program is allowed to do when it runs.

## Signatures

Every function spells out its parameter types and its return type. Locals inside the body are inferred, so the signature is the only place types are written.

```canon
fn clamp(n: Int, lo: Int, hi: Int) -> Int {
  return min(max(n, lo), hi)
}

test "clamp" {
  assert(clamp(15, 0, 10) == 10)
}
```

A missing return type is a parse error (P001). A function whose return type is not `Unit` must return on every path (T005). A `Unit` function may fall off the end, or use a bare `return`.

Generic functions name their type parameters in square brackets:

```canon
fn first_or[T](xs: List[T], fallback: T) -> T {
  return match first(xs) {
    Some(x) => x,
    None => fallback,
  }
}

test "first_or" {
  assert(first_or([], 7) == 7)
  assert(first_or(["a"], "b") == "a")
}
```

There is no overloading: a user function may not reuse a standard library name (T001), and each name means one function.

## Clauses

Three optional clauses sit between the signature and the body, each on its own line, always in this order: `effects`, `requires`, `ensures`. When a function has any clause, its opening brace moves to its own line.

```canon
fn withdraw(balance: Int, amount: Int) -> Int
  requires: amount > 0 && amount <= balance
  ensures: result >= 0
{
  return balance - amount
}

test "withdraw" {
  assert(withdraw(10, 3) == 7)
}
```

The formatter puts clauses in that order, sorts effect names, and merges two `requires` (or two `ensures`) lines into one joined with `&&`.

## Effects

An effect is a kind of side effect. There are five, and pure is the default: leaving out the `effects` clause means the function has none.

| Effect | Built-ins that use it |
|---|---|
| `fs` | `read_file`, `write_file` |
| `io` | `print`, `read_line` |
| `net` | `http_get`, `http_post` |
| `rand` | `random`, `random_int` |
| `time` | `now`, `sleep` |

A function lists exactly the effects it uses, no more and no fewer, in alphabetical order. Effects propagate: calling a function that declares `io` uses `io`, and so does naming an effectful function as a value (`map(names, print)`) or calling one inside a lambda (`map(names, |n| print(n))`).

```canon
fn log_all(lines: List[String]) -> Unit
  effects: io
{
  for line in lines {
    print(line)
  }
}

fn stamp(lines: List[String]) -> Int
  effects: io, time
{
  log_all(lines)
  return now()
}
```

The checker enforces the list both ways, and both errors carry a patch that rewrites the clause (`canon check --fix` applies it):

- **E101**: the function uses an effect it does not declare.
- **E102**: the function declares an effect it never uses.
- **E100**: the clause names something that is not one of the five effects.

```canon
# expect: E101
fn greet(name: String) -> Unit {
  print(name)
}
```

```canon
# expect: E102
fn add(a: Int, b: Int) -> Int
  effects: net
{
  return a + b
}
```

## Effects in tests

Test blocks are effect-checked too, with one difference: under `canon test`, `io`, `time` and `rand` are virtual (output is captured, the clock starts at 0 and moves only through `sleep`, and random numbers come from a fixed seed), so a test uses them freely and never declares them. `fs` and `net` touch the real world, so a test that uses them declares them on the line after its name, exactly like a function:

```canon
test "the clock is virtual" {
  print("tests may print")
  sleep(250)
  assert(now() == 250)
}

test "reads a fixture"
  effects: fs
{
  let r = read_file("/tmp/fixture.txt")
  assert(r == r)
}
```

A test that reads a file without the line is E101, and the patch adds it. Declaring `io`, `time` or `rand` on a test is E102, because it needs none of them.

```canon
# expect: E101
test "reads a fixture" {
  let r = read_file("/tmp/fixture.txt")
  assert(r == r)
}
```

## Contracts

`requires` is a Bool expression over the parameters, checked on entry. `ensures` is a Bool expression checked on every return, where `result` names the returned value. A failure stops the program with a trap that names the function: R001 for `requires`, R002 for `ensures`.

```canon
fn halve(n: Int) -> Int
  requires: n % 2 == 0
{
  return n / 2
}

fn main() -> Unit
  effects: io
{
  print(to_string(halve(3)))
}
```

Running it prints the trap as one JSON line on stderr and exits with status 1:

```json
{"code":"R001","message":"requires failed in fn halve","line":2,"col":13,"stack":[{"fn":"halve","line":2,"col":13},{"fn":"main","line":10,"col":19}]}
```

`canon run --no-contracts` skips both checks; the same program then prints `1`.

Contracts must be pure. A clause that performs an effect, directly or through a function it calls, is E103: an effect hidden in a contract would appear in no signature, and would happen or not depending on `--no-contracts`. Compute the value in the body instead.

```canon
# expect: E103
fn wait_for(n: Int) -> Int
  requires: now() >= 0
{
  return n
}
```

## Contract fuzzing

`canon test` runs the test blocks, then fuzzes contracts: every pure, non-generic function with a `requires` or `ensures` clause is called on 200 inputs generated from its parameter types. Ints, strings and lists are small (so a counterexample is readable), and the generator is seeded, so every run tries the same inputs. Inputs that fail the function's own `requires` are discarded; any other trap (a failed `ensures`, an `assert`, overflow, division by zero) is a counterexample.

```canon
fn abs_diff(a: Int, b: Int) -> Int
  ensures: result >= 0
{
  return a - b
}

fn halve(n: Int) -> Int
  requires: n % 2 == 0
  ensures: result * 2 == n
{
  return n / 2
}

fn apply_twice(f: fn(Int) -> Int, x: Int) -> Int
  ensures: result == result
{
  return f(f(x))
}

test "abs_diff of equal numbers" {
  assert(abs_diff(3, 3) == 0)
}
```

```text
PASS abs_diff of equal numbers
FAIL fuzz abs_diff: a = -19, b = 12
  {"code":"R002","message":"ensures failed in fn abs_diff","line":2,"col":12,"stack":[{"fn":"abs_diff","line":2,"col":12}]}
PASS fuzz halve (107 inputs)
SKIP fuzz apply_twice (a function-typed parameter)
2 passed, 1 failed
```

The test block passes, but the contract says what `abs_diff` promises, and the fuzzer found an input that breaks it. `halve` passed on every input its `requires` admits (the rest were discarded). A function whose parameters cannot be generated, such as a function type, is skipped. Functions with effects, generic functions and functions without a contract are not fuzzed. `canon test --no-contract-fuzz` runs only the test blocks.

## The entry point

`canon run file.cn` calls `fn main() -> Unit`, which may declare any effects. A `main` may instead return a `Result`; an `Err` prints `error: ` and its message on stderr and exits with status 1.

```canon
fn parse_port(s: String) -> Result[Int, Error] {
  let n = unwrap_or(parse_int(s), -1)
  if n < 1 || n > 65535 {
    return Err(Error { message: "bad port: " + s })
  }
  return Ok(n)
}

fn main() -> Result[Int, Error]
  effects: io
{
  let port = try parse_port("80x")
  print(to_string(port))
  return Ok(port)
}
```

This program prints `error: bad port: 80x` and exits 1.

## What the guarantee covers

The effects a checked program can perform are bounded by its entry point: `main`'s effects clause under `canon run`, and under `canon test`, each test's declared `fs` and `net` plus the virtual `io`, `time` and `rand`. The checker guarantees it, and at run time a capability guard enforces it again: the host performs only the effects the entry point declares, and contract fuzzing allows none. On a checked program the guard never fires; it is there in case the checker has a bug, and it reports R006 naming the entry point (`effect fs denied (write_file): fn main does not declare it`). `--no-capability-guard` turns it off for experiments.

Since v0.4 the guarantee also holds per function, because function types carry effects. `fn(String) -> Unit` is a pure function type, and `fn(String) -> Unit effects: io` is one whose calls perform `io`. Passing an effectful function where a pure function type is expected is T011, whether it goes through a parameter, a record field, a list, a lambda or a return value:

```canon
# expect: T011
fn apply(f: fn(String) -> Unit, s: String) -> Unit {
  f(s)
}

fn main() -> Unit
  effects: io
{
  apply(print, "apply's signature says it is pure")
}
```

To accept an effectful function, write its effects in the function type. Calling a function value performs its type's effects, so `apply` declares `io` too (E101 if it does not):

```canon
fn apply(f: fn(String) -> Unit effects: io, s: String) -> Unit
  effects: io
{
  f(s)
}

fn main() -> Unit
  effects: io
{
  apply(print, "the effect shows in every signature on the way")
}
```

The standard library's higher-order functions (`map`, `filter`, `fold`, `sort_by`, ...) take pure functions, so `map(xs, print)` is T011. Use a `for` loop to perform an effect per item. `--no-fn-effects` (or `--v0.3`) turns function-type effects off, for experiments.
