title: Use Canon with your agent
description: Give a coding agent the Canon reference, tell it to run the check and fix loop, and read the compiler's JSON output.

This page shows how to set up a coding agent to write Canon: give it the reference, give it the loop, and know what the compiler sends back. The loop is three commands:

```bash
canon check --json app.cn    # read the diagnostics
patch -p1 < fix.diff         # apply each fix the compiler ships
canon check --json app.cn    # repeat until "ok": true
```

Since v0.3 the compiler can apply the mechanical fixes itself, so the agent only sees what needs its judgment:

```bash
canon check --fix --write --json app.cn    # layout, effect lists, Int/Float: fixed and saved
```

## 1. Give the agent the reference

The whole language fits on one page, small enough to fit in a single prompt. It is the [Agent reference](/docs/for-agents), served as plain text at:

```text
https://canon-lake.vercel.app/llms.txt
```

If your agent can fetch URLs, point it there. If not, paste the text into its instructions or the first message. Agents learn Canon from this page alone ([Research](/research) has the data), and every example in it passes `canon check`.

## 2. Give the agent the loop

Put this in the instruction file your agent reads at the start of a session: `CLAUDE.md` for Claude Code, `AGENTS.md` for Codex and other tools that read it, or a project rule in Cursor.

```markdown
## Canon

This project is written in Canon (.cn files). Before writing Canon, read the
language reference at https://canon-lake.vercel.app/llms.txt.

After every change to a .cn file:
1. Run `canon check --fix --write --json FILE`. It applies every mechanical
   fix itself and reports only the problems that need you.
2. For each remaining diagnostic with a `fix`, apply `fix.diff` exactly as given
   (it is a unified diff; `patch -p1` applies it from the project root).
   Do not rewrite the code by hand when a fix is given.
3. For H001 (a hole), replace the `?` with a value of type `data.expected`,
   often a call to one of `data.candidates`.
4. For T001 with `data.suggestions`, apply the candidate `diff` that matches
   what you meant. For any other code, change the code as the message says.
5. Run step 1 again. Repeat until it prints "ok": true.

Then run `canon test FILE`. Never edit a test to make it pass.
```

If `canon` is not installed globally, write `npx canon-lang` in its place.

## 3. Read the JSON

`canon check --json FILE` prints one object per file. Here is the real output for a `main` that prints without declaring it:

```json
{
  "ok": false,
  "canonical": true,
  "diagnostics": [
    {
      "code": "E101",
      "severity": "error",
      "message": "fn main uses effects it does not declare: io (via print)",
      "line": 1,
      "col": 4,
      "fix": {
        "kind": "patch",
        "diff": "--- a/hello.cn\n+++ b/hello.cn\n@@ -1,3 +1,5 @@\n-fn main() -> Unit {\n+fn main() -> Unit\n+  effects: io\n+{\n   print(\"hello, canon\")\n }\n"
      },
      "data": {
        "missing": [
          "io"
        ]
      }
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `ok` | `true` when the file has no diagnostics |
| `canonical` | `true` when the file is already in the formatter's one standard layout |
| `diagnostics[].code` | A stable code such as E101; look it up in [Errors and fixes](/docs/diagnostics) |
| `diagnostics[].severity` | Always `error` today |
| `diagnostics[].message` | One line for people |
| `diagnostics[].line`, `.col` | Position, counting from 1 |
| `diagnostics[].fix.kind` | `patch` when a mechanical fix exists |
| `diagnostics[].fix.diff` | The fix as a unified diff against the file as checked |
| `diagnostics[].data` | Extra facts for some codes, such as `missing`, `unused`, `expected`, `candidates` |

Several patches can come back at once. Each is computed against the file as checked, so apply them in order; if one no longer applies, check again and use the new patch.

## Holes: ask the compiler

A hole is a `?` (or a named `?best`) written where the agent is unsure what expression goes. The compiler does not patch a hole. It reports H001 with the type the hole needs and the functions in the file that return that type:

```json
{
  "code": "H001",
  "severity": "error",
  "message": "hole ?best in fn score: needs a value of type Int",
  "line": 6,
  "col": 10,
  "data": {
    "expected": "Int",
    "candidates": [
      "total(xs: List[Int]) -> Int"
    ]
  }
}
```

A file with holes does not run. See [Holes](/docs/guide/holes).

## Tips for any agent tool

- **Load the reference every session.** Agents have not seen Canon in training. Keep the reference in the project instructions, not in a message that scrolls away.
- **Let the agent run commands.** The loop only works if the agent can run `canon check` and read its output. Allow the `canon` command (or `npx canon-lang`) in the tool's permission settings.
- **Prefer `--json`.** Text output is for people; the JSON keeps every field and the exact diff.
- **Apply, do not retype.** A patch fixes the problem and any layout drift together. Retyping a fix by hand can introduce a layout error (C001).
- **Ask for holes.** Tell the agent it may write `?` when unsure and use the H001 answer, rather than guess.
- **Check before running.** `canon run` refuses a file with diagnostics, so the agent loses nothing by checking first.
